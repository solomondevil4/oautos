# OAS 开发报告流程

> 强制规则见 `.codebuddy/rules/10-dev-template.md`。本 Skill 讲**每一栏怎么填、填到什么程度算合格**。

## 核心态度

**不许看到 Bug 就直接改。**

OAS 是"看屏幕点屏幕"的程序，绝大多数"看起来是 A 的问题"实际根因在 B。
本项目已有两次因猜测出错的记录（`instance_guard`、`_exit_matcher`）—— 报告的意义就是**逼自己先把源码读完**。

## 什么时候用

- 修 Bug（最常见）
- 新增功能 / 新增玩法
- 改玩法逻辑
- 从别的仓库移植功能
- 任何"改一下让它能…"的需求

**不适用**：纯问答（"这个文件是干什么的"）、纯调查任务、只读分析。

## 工作流程

```
1. 复制 TEMPLATE.md 作为骨架
2. 逐栏填写 —— 卡住就回去读源码，不许留空、不许猜
3. 关键栏无"待确认" → 报告完成
4. 判级：只碰 C/D 级 → 展示报告后动手
        碰了 A/B 级 → 只交报告，等人工确认
5. 改完 → 走 oas-code-review + oas-regression
```

## 13 栏填写指引

### 【问题】
用户原话 + 你复述的现象。**不要用你的猜测污染这一栏**。
合格：`斗技打到一半退出，日志停在 "Duel: wait battle"`

### 【相关文件】
`文件:行号 —— 一句话说明它在链路上干什么`。
每个文件都要真的打开过。自动生成的文件要标注（`assets.py` 是生成器产物）。

### 【调用链】
从入口到出错点的实际调用路径，形如：
```
script.py:479 loop() → get_next_task() → script.py:459 run() → load_module
→ tasks/Duel/script_task.py:XX run() → self.appear(I_XXX)
→ module/atom/image.py:256 match() → RPC 22269
```
**必须 grep 过**。参考 `oas-architecture` 的分层图判断在哪一层断掉。

### 【当前行为】
**代码实际会做什么**，不是"我觉得它想做什么"。
要引用具体行号。若依赖运行期行为（识别结果、时序）而无法静态确认 → 写"待确认：需看日志/实机"。

### 【预期行为】
期望它做什么。与【当前行为】的**差距**就是问题所在。

### 【根本原因】
**最容易被写坏的一栏。** 必须能回答"为什么会出现"，而不是"哪里不对"。

不合格：`识别失败了` （这是现象）
合格：`I_XXX 的 roi_front 被上一个任务匹配成功后回写到了左侧坐标（atom/image.py:178），本任务沿用旧坐标，点在空气上`

若确实查不出 → 写"**待确认**"，并列出 2-3 个候选原因 + 各自需要读哪个文件来排除。**此时不许动手。**

### 【hurry2实现】
**hurry2 是当前基线**（`E:\yyshurry2fork\OnmyojiAutoScript`，分支 `Forme`，HEAD `5567a78c`）。
这一栏写 hurry2 现在是怎么做的 —— 它是"正确行为"的参照系。
若 hurry2 这块本身就有已知活 bug（如 `tasks/GameUi/registry.py:82` 的 `for module_name in ("page")`），要写明。

### 【AzurTian/runhey参考】
> 注：仓库实际名是 **AzurTian**（无 e），你之前写作 AzureTian。

这两个**只是参考来源，不是权威**。写清楚三点：
1. 对方是怎么做的
2. **对方是上游还是下游** —— AzurTian 是 Hurry2 的**下游**（最后提交 = `Merge PR #296 from Hurry2/mine-pr`），它的任何"更新"都可能是抄过来的
3. 结论：合 / 不合 / 待确认（判断方法见 `oas-git-history`）

若这块跟对方无关 → 写"不涉及"，不要硬凑。

### 【推荐方案】
**至少 2 个方案（含"不改"）**，逐个比较：

| 方案 | 改几行 | 碰哪些文件（级别） | 风险 | 副作用 |
|---|---|---|---|---|
| A：… | | | | |
| B：… | | | | |

然后选一个，并说明**为什么选它**。
默认权重：**改动行数 > 文件级别 > 代码优雅度**。更优雅但要多改 3 个文件 → 选丑的。

### 【准备修改的文件】
清单式：`路径 —— 第 X 行附近 —— 改什么`。
**禁编辑清单**：`tasks/*/assets.py`（86 个）、`fluentui/`、`bin/`。

### 【预计影响】
沿用 `oas-regression` 的口径：
- 引用面：`grep -rl "<符号>" --include=*.py . | wc -l`（写实数）
- 继承方数量（改组件时必写）
- 受影响的其它任务清单
- 是否跨进程边界（脚本 ↔ 22269 ↔ 22268）

### 【测试方法】
**不许写"跑一下看看"。** 要具体到：
- 静态：`python -c "import tasks.<Name>.script_task"` 或资源校验命令
- 实机：进哪个界面、点什么、看哪行日志、日志里应该出现什么
- 若 AI 无法实机（当前环境无 `config/` 运行配置、无 `log/`、无模拟器）→ **写明"AI 未实机验证"** + 用户需要做的步骤

## 常见错误

| 错误 | 后果 |
|---|---|
| 【根本原因】写成现象 | 修了表面，问题复发 |
| 只给一个方案 | 用户没法判断代价 |
| 【调用链】靠记忆写 | 链是断的，改错地方 |
| 【AzurTian/runhey参考】默认认为对方更对 | 合进下游代码 = 回退三个月 |
| 【测试方法】写"应该没问题" | 假验证 |
| 先改后补报告 | 等于没做，且容易改错方向 |

## 禁止事项

- 报告没写完就动手
- 关键栏留"待确认"还继续改
- 用"应该是 X"当结论
- 方案中默认选改动最大的那个（理由是"更彻底"）

## 完成后如何验证

对照 `TEMPLATE.md` 自查：
- 13 栏全部填完，无空栏
- 【调用链】【当前行为】【根本原因】**没有**"待确认"
- 【推荐方案】有 ≥2 个方案 + 选择理由
- 【预计影响】的数字是 grep 出的实数
- 【测试方法】可执行（具体命令 / 具体界面 / 看哪行日志）

然后按规则判级：碰 A/B 级 → 只交报告等确认；只碰 C/D 级 → 展示报告后动手。
