# 开发报告前置制度

## 一句话

**不许看到 Bug 就直接改。** 任何 OAS 功能开发 / 缺陷修复 / 跨仓库移植，都要先把下面 13 栏报告写完，再谈改代码。

本文件是 `08-ai-behavior.md` 的**前置关口**——它规定"动手前先交报告"，`08` 规定"动手后怎么交付"。两者不冲突，是前后两道闸。

## 13 栏模板（一次不能少）

```
【问题】【相关文件】【调用链】【当前行为】【预期行为】【根本原因】
【hurry2实现】【AzurTian/runhey参考】【推荐方案】
【准备修改的文件】【预计影响】【测试方法】
```

完整填写指引见 `.codebuddy/skills/oas-dev-template/SKILL.md`；空白模板可直接复制 `.codebuddy/skills/oas-dev-template/TEMPLATE.md`。

## 四条硬规定

### 1. 不许猜 —— 猜了就继续读源码

报告里任何一栏，**只要是基于文件名 / 命名 / 经验推断出来的，就必须继续 Read / Grep 核实**。

- 核实不了 → 该栏写"**待确认**：<缺什么信息>"，**不许写"应该是""大概率"**
- 关键栏（【调用链】【当前行为】【根本原因】）若标了"待确认"，**报告不算完成，不许动手**
- 本项目已两次因猜测出错（`instance_guard`、`_exit_matcher`）

### 2. 多方案必须比较

【推荐方案】里至少要列 **2 个可选方案**（含"不改"这个选项），逐个写明：改几行、碰哪几级文件、风险、副作用。只有一个方案时，要说明为什么没有其他选择。

### 3. 默认选"改得最少"的那个

方案排序的默认权重：**改动行数 > 文件级别 > 代码优雅度**。
一个方案更优雅但要多改 3 个文件 → 选丑的那个。

### 4. 报告通过才动手

| 情况 | 是否可以直接改 |
|---|---|
| 报告里只碰 🟡 C / 🟢 D 级文件 | 展示报告后可改 |
| 报告里碰了 🔴 A / 🟠 B 级文件 | **必须等人工确认后再改**，只交报告不动手 |
| 报告里有"待确认" | 不许改，先补核实 |
| 用户明确说"照方案 X 改" | 按 X 改 |

## 禁止事项

- ❌ 跳过报告直接上手改（哪怕改动很小）
- ❌ 先改了再补报告（等于没做）
- ❌ 报告里写"应该是 X 导致的"当结论
- ❌ 只给一个方案不给比较
- ❌ 把【测试方法】写成"跑一下看看"（要写具体命令 / 具体界面 / 看哪行日志）
