# 图像识别与 OCR 规范

## 先记住：识别不在脚本里算

- 图像服务 `127.0.0.1:22269`（`module/image/rpc.py` + `runtime.py`）
- OCR 服务 `127.0.0.1:22268`（`module/ocr/rpc.py`，底层 ppocronnx）
- 截图后只上传一次，换回一个 `frame_id`；之后所有找图/读字都靠这个编号远程调用
- 服务端带帧缓存 + 模板缓存 + 多线程 worker
- **没有本地兜底**——`ensure_image_server_ready()` / `ensure_ocr_server_ready()` 连不上直接抛 `ScriptError`

> 所以"服务没起来"和"识别不准"是两种完全不同的故障。排查时先确认服务活着。

## ⚠️ 头号风险：`roi_front` 跨任务污染

`tasks/*/assets.py` 里的 **2198 个 `RuleImage` + 302 个 `RuleOcr` 全是模块级全局单例**——整个程序只有一份。

`module/atom/image.py:180-182`：匹配成功后会把服务端算出的 `roi_front` **回写**到这个对象上。

后果：A 任务在屏幕左边找到过这张图 → 对象记住了左边 → B 任务再找这张图时会优先在左边找 → 找不到就点错地方。

**AI 看代码时会以为 `roi_front` 是每个任务独立的变量——它不是。而且单任务测试永远测不出这个问题。**

## `assets.py` 禁止手改

文件头写着 `# This file was automatically generated by ./dev_tools/assets_extract.py.` / `# Don't modify it manually.`

流程必须是：

```
放素材图 → 改 image.json / ocr.json → python dev_tools/assets_extract.py → 生成 assets.py
```

`assets_extract.py` **无参数全量跑**，会重写全仓库 86 个 `assets.py`。跑之前心里有数。

## 规则类型不止"找图"

`RuleImage`（找图）、`RuleClick`、`RuleLongClick`、`RuleSwipe`、`RuleList`（列表翻找）、`RuleGif`、`RuleAnimate`（判断动画是否停稳）、`ImageGrid`、`RuleScatter`（多边形正态散点）。

## OCR 六种模式（`module/ocr/base_ocr.py`）

整段 / 单词 / 数字 / 计数（形如 `3/5`）/ 时长（形如 `01:23`）/ 数量（带单位）。

选错模式是 OCR 问题最常见的原因——不要用整段模式去读数字。

## 常见错误与正确做法

| 症状 | 别这么干 | 应该这么干 |
|---|---|---|
| 认不出来 | 调低 threshold 让它"认出来" | **换更稳定的标志物**（治本） |
| 时灵时不灵 | 继续调 ROI | ROI 避开会飘的 UI（气泡、红点） |
| 页面提前命中 | 继续加图 | `any_of()` 里不能混入非唯一图 |
| 操作后读到旧数字 | 加大 sleep | **sleep + 重新截图**再读 |
| 疯狂点空气 | 加重试 | 检查**模板图是否缺失/损坏**——模板非法时 `appear()` 反而返回"找到了" |

## 排查要点

- `appear()` **匹配失败是静默的，不打日志**。查日志时看不到"没找到"，只能看到后续动作不对——不要误判成"根本没执行"
- 调试工具：`dev_tools/assets_test.py` —— **它没有命令行参数**，`__main__` 里是别人硬编码的桌面路径。**正确用法是调用它的函数**：`detect_image(<图片绝对路径>, <RuleImage对象>)` / `detect_ocr(<图片绝对路径>, <RuleOcr对象>)`，返回 bool 或 OCR 结果
- 服务开关在 `deploy/config.py`：`StartImageServer` / `ImageClientAddress` / `OcrClientAddress`

## 禁止事项

- 手改 `assets.py`
- 给 RPC 调用加 try/except 兜底
- 删除或改名已有的 `I_XXX` / `O_XXX`（可能被别的任务引用）
- 用正则硬凑 OCR 结果（应在模式层解决）
